# docs/ 文档格式规范

本文件是 record-session 技能的内置默认格式规范. 当项目没有 `docs/AGENTS.md` 或 `docs/CLAUDE.md` 时使用.

当你在 `docs/` 下创建或修改任何 Markdown 文档时, 必须严格遵守以下规范.

## Frontmatter 格式

普通业务文档必须包含 YAML frontmatter:

```yaml
---
description: "一句话简介, 帮助 AI 快速了解文档内容"
related:
  - docs/shared/数据口径.md | 数据口径来源
  - docs/example_topic/0615_前置实验结论.md | 前置实验结论
sessions:
  - <ai_tool> | <session_id> | <修改内容, 20字以内> | <YYYY-MM-DD HH:MM>
---
```

- `description` 用于快速判断文档相关性, 无需阅读全文
- `related` 可选, 只列当前文档参考的文档
  - 每行格式: `<项目根相对路径> | <一句话说明关联原因>`
  - 路径统一相对于项目根目录, 如 `docs/shared/数据表总览.md`
  - 不放代码、SQL、output, 这些入口写在正文
  - 关联为单向引用, 不要求双向维护
  - 每个普通文档最多 5 条 related, 最相关排前面
- `sessions` 记录修改的会话来源, 便于追溯
  - 每行格式: `<ai_tool> | <session_id> | <修改内容, 20字以内> | <YYYY-MM-DD HH:MM>`
  - `ai_tool` 使用短标识, 如 `cc` 表示 Claude Code, `codex` 表示 Codex
  - 每个普通文档最多保留最近 3 条 sessions, 新记录排第一
  - 同一文档中同一个 session id 只能出现一次, 同一会话多次修改时合并修改内容并更新时间
  - 合并重复 session 时必须保留被合并记录的主要修改内容, 禁止只写"合并重复session"
  - 禁止使用 `current`、环境变量占位符或缺分钟时间
  - 写入或更新 `sessions` 前, 必须先执行 `echo $CODEX_THREAD_ID` 或 `echo $CLAUDE_CODE_SESSION_ID` 获取真实输出, 禁止凭记忆填写 session id

### `docs/onboard.md` 例外

`docs/onboard.md` 是项目 onboard 缓存摘要, 不是普通事实文档. 它由 `docs/index.md`、各主题 `index.md` 和其他文档 frontmatter 汇总生成, 用于降低每次 onboard 的上下文占用.

该文件不维护 `related` 和 `sessions`, 刷新时只覆盖缓存元信息和摘要正文. frontmatter 必须使用:

```yaml
---
description: "项目 onboard 缓存摘要, 由 docs 索引和文档 frontmatter 生成"
generated_at: "YYYY-MM-DD HH:MM"
source_latest_session_at: "YYYY-MM-DD HH:MM"
source_latest_doc: "docs/path/to/latest.md"
---
```

- `generated_at` 表示缓存摘要生成时间
- `source_latest_session_at` 表示生成时看到的最新业务文档 session 时间
- `source_latest_doc` 表示生成时最新 session 所在文档
- 普通 onboard 不自动修改该文件, 只有用户明确要求刷新 onboard 摘要时才更新
- 正文控制在 60 行以内, 只保留项目定位、主题状态、最近活跃文档、读取路线和摘要来源

AI 工具名、Session ID 和时间获取:

```bash
# Claude Code
echo cc
echo $CLAUDE_CODE_SESSION_ID

# Codex
echo codex
echo $CODEX_THREAD_ID

date -u -v+8H "+%Y-%m-%d %H:%M"
```

## 目录组织

- 按业务主题划分 `docs/` 子目录, 目录名使用英文 snake_case
- 跨主题公用的稳定参考内容放入 `docs/shared/`, 优先使 用语义文件名
- Prompt、工作流和其他原始产物放入对应主题的专用目录, 不强制套用正文文档结构
- 已归档历史文档移动到 `archive/docs/<原docs子目录>/`
- 项目可以在 `docs/AGENTS.md` 中补充或覆盖具体目录用途

`.nomedia` 是 Obsidian 或移动端环境可能自动添加的媒体扫描控制文件, 文档维护流程不创建、不删除、不维护该文件.

## 文件命名

- 普通工作文档使用 `MMDD_短标题.md`, 如 `0630_精排知识补充线上改造.md`
- 文件名前缀表示创建日期, 后续更新不改名前缀
- `docs/shared/` 的稳定参考文档优先保留语义名
- `index.md`, `onboard.md`, `AGENTS.md`, `CLAUDE.md` 不改名
- 目录名用英文 snake_case

## Index 约定

- 各目录 `index.md` 负责说明哪些文档当前该读
- `index.md` frontmatter 只保留 `description`
- 建议表格列: `文档`, `定位`, `状态`
- 状态只在 index 里维护: `current`, `superseded`, `archive`
- 判断文档新旧看文件名前缀, 判断是否还有效看 index 状态
- `index.md` 不维护 `related` 和 `sessions`, 避免导航文档 header 变长
- 已移动归档的文档, 原目录 `index.md` 中路径写为 `archive/docs/<原docs子目录>/<文件名>.md`, 状态写 `archive`
- `archive/docs/<子目录>/index.md` 维护该目录历史文档清单

## 生命周期约定

- `current`: 当前该读的权威文档
- `superseded`: 已被后续文档替代, 但尚未确认合并或归档
- `archive`: 历史文档, 原文应移动到 `archive/docs/<原docs子目录>/`
- 归档时不在 `docs/` 原路径保留 stub 文件
- 合并旧文档时, 优先把仍有效内容并入现有 `current` 主文档
- 重命名普通工作文档时, 保留 `MMDD_` 创建日期前缀, 只修改标题后缀
- 删除文档内废弃内容前, 必须先列出章节、删除原因、替代来源和影响范围, 经用户确认后再删
- 移动、重命名、合并、归档、删除前, 必须同步计划更新 `index.md`, `related` 和正文路径引用

## 写作约定

- 中文 H1 顶级标题
- H2 标题根据文档类型和实际内容命名, 不强制中文编号或固定措辞
- 表名、字段名、代码标识符用反引号
- 文档路径使用项目根相对路径, 不用 `../`
- 跨主题公用的参考内容放 `docs/shared/`

### 文档类型选择

普通正文文档根据主要回答的问题选择一种主要类型:

| 主要问题 | 文档类型 | 第一屏重点 |
|---|---|---|
| 我们发现了什么, 为什么 | 分析报告 | 核心结论 |
| 准备解决什么, 建议怎么做或验证什么 | 方案计划 | 目标、推荐方案或待验证假设 |
| 现在做到哪里, 下一步是什么 | 执行进展 | 当前状态和下一步 |
| 当前事实、概念和口径是什么 | 参考说明 | 用途与适用范围 |
| 怎样稳定地重复完成这件事 | 操作指南 | 适用场景和前置条件 |

- 一份文档只设置一种主要类型, 可以包含少量辅助内容
- 同一会话产生多个不同类型的持久成果时, 只有需要独立维护时才拆分文档
- 第一屏直接回答该类型最重要的问题, 不强制使用固定标题
- 只创建实际有内容的章节, 不为套模板生成空章节
- `index.md`、`onboard.md`、Prompt 原文和其他原始产物使用专门规则, 不归入五类正文文档
- 不因规范变化批量重排旧文档; 旧文档被实质更新时再按其主要类型逐步调整

### 分析报告

用于实验结果、数据分析、问题诊断和复盘, 重点回答“发现了什么以及为什么”. 推荐结构:

```markdown
## 核心结论
## 分析范围与数据口径
## 关键证据
## 使用边界与建议
## 产物索引
```

- 结论存在多个独立判断时再分点, 不强制使用“结论 1”
- 每个重要结论紧跟数据、规则或真实案例, 同时说明不能外推到什么范围
- 现有分析报告使用“当前结论”作为标题仍然合规

### 方案计划

用于改造方案、实验计划和落地规划, 重点回答“为什么做、准备怎么做、如何判断完成”. 推荐结构:

```markdown
## 目标与待解决问题
## 推荐方案或待验证假设
## 范围与非目标
## 实施与验证方法
## 验收标准
## 风险与待决策项
```

- 方案型文档突出推荐做法和选择原因
- 实验计划突出假设、变量、指标和停止条件
- 尚未得到结果时不制造结论

### 执行进展

用于上线执行、长期任务跟进、运行记录和排障, 重点回答“当前状态和下一步”. 推荐结构:

```markdown
## 当前状态
## 已完成工作
## 当前问题
## 下一步
## 关键产物与验证结果
## 执行记录
```

- 每次更新都同步刷新顶部的当前阶段、已完成、阻塞和下一步
- `执行记录` 可以按时间追加, 但顶部状态必须保持为最新事实
- 工作完成后, 将稳定结论或可复用步骤分别沉淀到分析报告、参考说明或操作指南

### 参考说明

用于架构、字段、表、概念和统计口径等稳定事实, 重点回答“当前是什么”. 推荐结构:

```markdown
## 用途与适用范围
## 整体结构或核心概念
## 详细说明
## 示例
## 来源与维护说明
```

- 按读者查询路径组织内容, 不要求结论先行
- 正文只保留当前有效事实, 不积累每日进展或修改流水
- 明确每个概念能说明什么、不能说明什么

### 操作指南

用于可重复执行的操作流程, 重点回答“怎样稳定完成”. 推荐结构:

```markdown
## 适用场景
## 前置条件
## 操作步骤
## 验证方法
## 常见问题与恢复方式
## 输出产物
```

- 步骤按真实执行顺序编写, 关键命令和输入输出必须可定位
- 同时写明成功判断、常见失败原因和恢复方法
- 不把一次性的执行进度混入稳定操作步骤

### 数据、判断和案例说明

- 分析报告中的重要结论必须有数据、规则或真实案例支撑, 不能只写判断
- 每张核心数据表附近必须说明数据来源、时间窗口或分区、过滤条件、统计粒度、公式、样本限制或排除项
- 百分比变化必须写清是百分点 `pp` 还是相对比例变化
- delta 必须写明计算方向, 如 `实验组 - 对照组`
- 规则型结论必须贴近说明阈值、命中条件和不适用场景
- 结论有外推限制时, 必须在结论附近写明使用边界

### 长文压缩

- 长过程、排错流水、历史执行细节默认压缩到 `执行记录`、`附录` 或 `产物索引`
- 已被新结论替代的旧结论不机械保留; 如需保留, 必须写明替代来源和历史价值
- 代码、SQL、output、data 路径不放 `related`, 放正文的产物索引或对应口径说明中

## 内容质量要求

- 简洁, 不写废话, 直接进入主题
- 面向后续 AI 阅读, 需要包含足够上下文
- 包含具体的表名、字段名、代码路径等可定位信息
- SQL 示例必须指定分区条件
- 记录"为什么"而不仅仅是"是什么"
- 第一屏必须回答选定文档类型最重要的问题
- 分析报告的结论和数据必须就近说明证据、计算口径、判断规则和使用边界
- 方案计划必须说明目标、范围和验收标准
- 执行进展必须保持顶部状态和下一步为最新事实
- 参考说明只保留当前有效定义, 操作指南只保留可重复执行的稳定步骤
- 修改已有文档时默认整合和替换过时内容, 不机械追加
- 已确认废弃的过程、计划或旧结论可以删除, 但删除前必须得到用户确认
