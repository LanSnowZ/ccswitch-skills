# record-session

将当前会话中值得长期保留的工作内容沉淀到项目 `docs/` 目录中, 供人和后续 AI 共同阅读.

## 执行流程

### 第一步: 回顾当前会话

总结本次对话中完成的关键工作, 只提炼值得长期保留的内容:

- **做了什么**: 具体的任务和操作
- **结论**: 得到了什么发现或决策
- **方案**: 确认了什么目标、设计或验证方法
- **进展**: 当前做到哪里、有什么阻塞、下一步是什么
- **参考知识**: 哪些稳定事实、概念、字段或口径需要复用
- **经验**: 踩坑记录、注意事项、可复用的模式

### 第二步: 加载文档格式规范

按优先级依次检测, 使用第一个找到的规范:

1. **项目规范(优先)**: 检查项目中是否存在 `docs/AGENTS.md` 或 `docs/CLAUDE.md`
   - 如果存在 `docs/AGENTS.md`, 优先遵守它
   - 如果只存在 `docs/CLAUDE.md`, 遵守 `docs/CLAUDE.md`
   - 两者同时存在时, 视为同一规范, 如内容冲突则优先 `docs/AGENTS.md`

2. **内置默认规范(回退)**: 如果项目中不存在上述规范
   - 读取 `~/.cc-switch/skills/record-session/references/format_default.md` 作为默认格式规范
   - 使用默认规范前, 先询问用户是否保存到项目 `docs/AGENTS.md`

### 第三步: 判断文档类型

根据文档主要回答的问题选择一种主要类型:

| 主要问题 | 文档类型 |
|---|---|
| 我们发现了什么, 为什么 | 分析报告 |
| 准备解决什么, 建议怎么做或验证什么 | 方案计划 |
| 现在做到哪里, 下一步是什么 | 执行进展 |
| 当前事实、概念和口径是什么 | 参考说明 |
| 怎样稳定地重复完成这件事 | 操作指南 |

- 一份文档只设置一种主要类型, 可以包含少量辅助内容
- 同一会话产生多个不同类型的持久成果时, 只有在它们需要独立维护或更新节奏明显不同时才拆分文档
- `index.md`、`onboard.md`、Prompt 原文和其他原始产物遵守格式规范中的例外规则, 不强行归入五类正文文档
- 更新已有文档时先判断它当前承担的主要角色, 不因规范变化单独重排旧文档
- 已有文档被实质更新且现有结构不适合其主要角色时, 在写入方案中说明需要调整的结构

### 第四步: 获取会话信息

写入前必须获取真实会话信息:

```bash
# Claude Code
echo cc
echo $CLAUDE_CODE_SESSION_ID

# Codex
echo codex
echo $CODEX_THREAD_ID

date -u -v+8H "+%Y-%m-%d %H:%M"
```

- Codex 必须使用真实 `$CODEX_THREAD_ID`, 禁止写 `current`
- Claude Code 必须使用真实 `$CLAUDE_CODE_SESSION_ID`, 禁止写 `${CLAUDE_CODE_SESSION_ID}`
- 如果无法获取真实 session id, 必须先询问用户, 不得自造占位符

### 第五步: 扫描现有文档结构

```bash
find docs/ -name "*.md" | head -80
```

阅读相关目录的 `index.md`, 再读取候选文档的 frontmatter 和标题树. 重点判断:

- 当前会话属于哪个主题目录
- 候选文档当前属于哪种主要类型
- 应新建、整合、替换还是归档
- 是否有已有文档可更新
- 当前目录的命名和状态约定

### 第六步: 与用户确认写入方案

将以下内容呈现给用户, 等待确认后才能写入:

- 操作类型: 新建 / 整合 / 替换 / 归档
- 文档类型: 分析报告 / 方案计划 / 执行进展 / 参考说明 / 操作指南 / 例外文档
- 类型选择原因: 说明这份文档主要回答什么问题
- 计划写入哪个文件
- 计划写入的内容摘要
- 采用的正文结构: 列出实际需要写入的章节
- 插入或替换位置
- 是否会删除过时内容

用户可能会修改方案或补充要求, 根据反馈调整后再执行写入. 未经用户确认, 不得写入或修改任何文档.

### 第七步: 执行写入

用户确认后, 按照已加载的格式规范和选定文档类型写入文档.

- 只创建当前内容需要的章节, 不生成空模板章节
- 保持第一屏直接回答该类型最重要的问题, 不强制所有文档使用相同标题
- 修改已有文档时按其主要类型整合内容, 不机械追加会话流水

## 普通文档约定

- 新建普通工作文档使用 `MMDD_短标题.md`, 例如 `0630_精排知识补充线上改造.md`
- 文件名前缀表示创建日期, 后续修改不改名前缀
- `docs/shared/` 的稳定参考文档优先保留语义名
- `index.md` frontmatter 只保留 `description`, 不维护 `related` 和 `sessions`
- `onboard.md`, `AGENTS.md`, `CLAUDE.md` 不维护普通文档的 `related`

## 补充已有文档的注意事项

- 先读完整个文档, 理解其结构和上下文
- 默认整合到逻辑上合适的位置, 不机械追加到末尾
- 如果旧结论已经过时, 可以替换或删除; 只有仍有复盘价值时才保留历史说明
- 保持与文档已有内容风格一致
- 更新普通文档 frontmatter 的 `sessions`, 最多保留最近 3 条, 新记录排第一
- 同一文档中同一个 session id 只能出现一次, 同一会话多次修改时合并修改内容并更新时间
- 合并重复 session 时必须保留被合并记录的主要修改内容, 禁止只写"合并重复session"
- 更新普通文档 frontmatter 的 `related`, 最多保留 5 条文档引用, 按相关性排序

## 新建文档的注意事项

- 确定放在哪个子目录下, 根据主题归属选择
- 如果需要新建子目录, 使用英文 snake_case 命名
- `.nomedia` 是 Obsidian 或移动端环境可能自动添加的媒体扫描控制文件, record-session 不创建、不删除、不维护
- 文件名使用 `MMDD_短标题.md`
- 确保 frontmatter 包含 `description`, `related`, `sessions`
- `related` 只放当前文档参考的文档, 不放代码、SQL、output
